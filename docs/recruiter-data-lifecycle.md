# 招聘数据生命周期

Web 控制台使用本地文件保存岗位、候选人评估、回复草稿、任务历史和审计日志。本文说明数据的创建、更新、当前/历史状态、删除和备份边界。

## 数据位置

默认目录：

```text
~/.boss-agent/recruiter-ai/
```

主要内容：

```text
jobs/                 岗位 JD 和评分规则
evaluations/          候选人简历、评分证据和人工阶段
replies/              待人工审核的回复草稿
web_tasks.db          Web 后台任务历史
audit.jsonl           关键操作审计记录
```

## 候选人版本与去重

BOSS 候选人优先使用平台提供的稳定候选人标识，例如 `geek_id`，再退到其他可用平台 ID。

本地文件上传优先使用**规范化来源路径**形成稳定候选人身份。简历内容指纹、岗位 JD 和评分规则指纹用于判断是否需要重评：

- 同一路径、简历/JD/rubric 都未变化：跳过重复 AI 评估；
- 同一路径简历内容更新：生成新评估版本；
- 岗位 JD 更新：即使 rubric 不变，也生成新评估版本；
- rubric 更新：生成新评估版本；
- 人工阶段和备注：按逻辑候选人跨评估版本同步和继承；
- 删除候选人：清理该 canonical identity 下的全部评估版本和关联草稿。

历史 `created_at` 可以来自不同版本，可能包含 `Z`、时区偏移或无时区格式。读取时会先转换为实际 UTC 时间，再选择逻辑候选人的最新版本；排行榜同分时也使用实际时间做 tie-break。

为避免将不同候选人错误合并，本地批量导入仍应使用唯一、稳定的文件路径或文件名，例如：

```text
candidate-001-zhang-san.pdf
candidate-002-li-si.docx
```

## 当前评估与 stale 历史

评估记录不会因为岗位配置变化而立即删除。对于已经保存的岗位，只有同时满足以下条件的最新候选人评估才属于**当前结果**：

- `jd_text` 与当前保存岗位一致；
- `rubric_fingerprint` 与当前保存评分规则一致。

如果岗位 JD 或 rubric 变化，之前的最新评估会变成 **stale**：

- 历史 JSON 仍保留用于审计；
- 不再进入当前 Web Dashboard、候选人排名、统计或 CSV；
- CLI `rank / report` 对已保存岗位同样只展示当前配置结果；
- `report` 和 Web 结果可返回/显示 `stale_count`；
- 重新评估后，新版本重新进入当前排名；
- 人工阶段和备注会继承到新版本。

没有保存岗位文件的 ad-hoc CLI 评估仍可以按 `job_key` 使用历史最新版本。岗位文件如果存在但损坏，则直接报错，不会把损坏状态伪装成 ad-hoc 模式并继续显示旧分数。

旧 JD、旧 rubric 或已经被新版本替代的 evaluation 不能继续用于生成新的 AI 回复草稿。Web 返回 `STALE_EVALUATION`，CLI 在加载 AI 配置/调用模型之前拒绝该 evaluation ID。

## 隐私处理

### 本地人工数据

本地可以保留招聘操作真正需要的信息，例如：

- 姓名；
- 电话和座机；
- 邮箱；
- 微信；
- QQ；
- 招聘阶段和人工备注；
- 招聘沟通上下文。

但以下高风险身份数据不属于日常约面需要，会在标准化和直接 Store 写入边界移除：

- 身份证号，包括连续以及常见空格/短横线格式；
- 护照号字段和带明确标签的护照号码；
- 家庭住址、现住址、居住地址、住宅地址等住宅详细地址。

`面试地址` 等招聘流程信息不会被住宅地址规则误删。

### AI 模型数据

发送给 AI 模型前，系统还会递归清理：

- 候选人姓名；
- 手机号、座机；
- 邮箱；
- 微信号；
- QQ；
- 身份证号、护照号、住宅地址；
- 年龄、出生日期、性别、照片、婚育等受保护属性；
- 民族/种族/国籍、宗教、政治身份、健康/残障等个人属性；
- 嵌套字段和 PDF/DOCX/TXT 自由文本中的上述内容。

回复草稿生成时，候选人身份和联系方式同样会从模型上下文中移除。回复记录落盘时，电话/邮箱/微信/QQ 等人工约面联系方式可以保留，但身份证、护照和住宅详细地址会再次清理。

本地原始评估记录仍可能包含招聘人员有权处理的简历内容，因此应把 `~/.boss-agent` 目录视为敏感业务数据并限制操作系统访问权限。

## 删除

### 删除候选人

候选人详情底部提供“永久删除”。操作会删除：

- 该逻辑候选人的全部历史评估；
- 与这些评估关联的全部回复草稿；
- 任务结果中对相关 evaluation 的可清理引用。

审计日志只保留删除动作和数量，不保留候选人姓名或人工备注原文。

### 删除岗位

岗位卡片提供“删除”。操作会删除：

- 岗位 JD 和评分规则；
- 岗位下全部候选人评估；
- 与这些评估关联的回复草稿。

任务历史和审计日志不会级联删除，用于证明发生过相应操作，但其中不保存 AI Key 或完整简历正文。

删除与筛选任务提交使用同一临界区。只要相关筛选处于 `queued / running / cancelling`，删除会被阻止；同时不会出现“删除检查通过后另一线程又插入新筛选任务”的 check-then-delete 竞态。

删除不可撤销。执行删除前应根据公司数据保留政策决定是否备份。

## 任务和审计数据

任务状态持久化在 SQLite：

- 使用 WAL；
- 服务重启会把遗留的运行中任务恢复为中断/取消终态；
- 活跃 `queued / running / cancelling` 任务有硬上限，避免无界增长；
- 协作取消不会强杀已经发出的第三方 HTTP 请求，但当前调用返回后不会继续下一位候选人。

审计日志是有界 JSONL：会按文件大小和保留条数裁剪。当前审计 metadata 保存操作摘要、数量、状态、provider/model 等必要信息，不用于保存 API Key、完整简历正文或候选人聊天全文。

## 备份与恢复

停止 Web 控制台后，复制整个数据目录即可完成一致性备份：

```text
~/.boss-agent/
```

恢复时：

1. 关闭 Web 控制台；
2. 将备份覆盖回原数据目录；
3. 重新启动控制台；
4. 在“任务与审计”确认历史记录可读取；
5. 如果岗位 JD/rubric 与历史评估不匹配，按页面 `stale_count` 重新执行筛选。

任务数据库使用 SQLite WAL 模式。进行文件级备份时应停止服务，或同时复制：

```text
web_tasks.db
web_tasks.db-wal
web_tasks.db-shm
```

## BOSS 登录是否必需

本地简历筛选不要求登录 BOSS。首次引导中的 BOSS 登录属于可选步骤，仅在需要读取授权范围内的 BOSS 投递、在线简历或聊天上下文时使用。
